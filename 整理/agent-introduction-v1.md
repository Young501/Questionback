# 什么是 Agent？与大模型有什么本质不同？

> 记住“自主闭环”：围绕目标做决策，调用工具执行，观察结果，再调整下一步。模型是决策组件，Agent 是包含执行、状态与反馈的系统。

来源：小林面试笔记 · 什么是 Agent？与大模型有什么本质不同？ · PDF 共 13 页

## 先记住一句话

- 记忆口诀：目标驱动，感知规划，工具行动，反馈调整。
- 区分层级：LLM 是模型；Agent 是组织模型、工具、状态和控制循环的系统。

Agent 是围绕目标运行的 AI 系统。它感知当前状态、规划下一步、通过工具采取行动，并根据执行结果继续决策，形成自主闭环。LLM 是其中负责理解、推理和生成的决策组件，不能把模型与完整系统混为一谈。

出处：PDF 第 1、4、5、13 页

## LLM 与 Agent：差别在系统层

| 比较维度 | 独立的模型调用 | Agent 系统 |
| --- | --- | --- |
| 交互方式 | 输入上下文，生成输出 | 围绕目标持续决定下一步 |
| 对外行动 | 生成调用请求或操作说明 | 由外部程序执行工具，获得真实结果 |
| 任务状态 | 只依据本次传入的上下文 | 维护执行轨迹、中间结果和相关记忆 |
| 结果反馈 | 一次调用结束后不会自行继续 | 观察成功或失败，决定继续、调整或结束 |

不要把“普通大模型完全不会规划”当成结论。模型本身可以输出计划，也能使用传入的对话上下文；区别在于，完整执行循环与跨调用状态需要系统来组织。这里比较的是独立模型调用与 Agent 系统，而不是所有聊天产品。

出处：PDF 第 2、3、9、13 页；边界澄清

## 未接外部能力时的三个限制

- 实时信息：模型参数不会因为外界发生新事件就自动更新；获取天气等实时数据需要外部信息来源。
- 真实行动：写出邮件正文不等于邮件已发送；需要运行程序调用发送接口。
- 持续状态：一次调用能利用传入的上下文，但没有显式保存和回传，就不能保证跨调用保留中间状态。

对应的系统补足：信息来源与工具、执行程序、任务状态与记忆。工具不等于长期记忆；记忆也不会凭空产生。

出处：PDF 第 2、3、6、9 页

## 运行闭环：感知 → 规划 → 行动 → 再感知

1. 感知：读取目标、当前任务状态、可用信息和上一步执行结果。
2. 规划：拆解任务，判断下一步是否需要工具、用哪个工具以及参数。
3. 行动：外部执行程序调用工具或服务，把决策落到真实环境中。
4. 再感知：读取返回结果，检查是否符合预期，调整计划或结束。

例子：收到“查询北京天气并形成播报”的目标，先查询天气，检查返回数据，再组织播报。若查询失败，就根据原因调整，而不是把想象中的天气当作已查询的结果。闭环的关键是结果影响后续决策，而不是只执行预先写好的步骤。

出处：PDF 第 4 至 7、9 页

## 工具调用：决策与执行分离

- 工具定义是一份接口说明：名称、用途、参数结构和必填项。定义本身不是执行代码。
- 模型根据目标与上下文决定工具名称和参数，生成结构化调用请求。
- 运行时或应用代码负责实际调用函数、API、数据库或代码执行器。
- 执行结果回传后，模型才能基于真实结果继续判断。

写出了 get_weather 的 JSON 参数，只表示形成了调用请求。只有执行程序完成调用并拿到结果，才能说“天气已查询”。同理，生成邮件内容或 send_email 请求都不等于邮件已发送。

出处：PDF 第 6 至 8 页

## 记忆：当前任务与跨任务分开看

| 记忆类型 | 主要保存什么 | 资料中的实现举例 |
| --- | --- | --- |
| 短期记忆 | 当前任务的搜索结果、计算结果、执行进度 | 当前上下文或任务状态 |
| 长期记忆 | 跨任务的用户偏好、历史操作记录 | 持久化存储，结合检索取回 |

记忆由系统保存、筛选并在需要时提供给模型，不是模型凭空记住所有历史。向量数据库与语义检索是原文给出的常见方式，不是长期记忆唯一可用的实现，也不是每个 Agent 必须配置的组件。

出处：PDF 第 9 页；实现边界澄清

## 多步推理与纠错：失败也要进入反馈

- 搜索无有效结果：观察结果后换关键词，而不是原样重复假设。
- 接口报参数错误：读错误信息，判断是否需要修正参数再调用。
- 步骤结束：检查结果与目标是否一致，必要时修改后续计划。

与固定流程对比时，重点是能根据观察动态决定后续行动。不要承诺 Agent 一定能修复所有错误或永远成功；“可以分析并调整”是系统能力，“每次都正确”是另一个问题。工程上还应设置终止条件或执行预算，防止无限重试（整理补充）。

出处：PDF 第 9 页；终止边界为整理补充

## 为什么更容易落地：三个条件

- 模型能力：理解复杂指令、任务拆解和多步决策的能力提升。
- 调用机制：结构化的工具请求减少手工解析模型输出的工程成本。
- 配套生态：开发框架、存储与检索、外部 API 等更完善。

这一节是原文对发展背景的归纳，不是 Agent 定义的组成条件。面试优先说明机制，再讨论生态。厂商、版本、组织归属与数量等时间信息不作为固定背诵重点。

出处：PDF 第 10 页

## MCP 与 A2A：一个接工具，一个协作

| 协议 | 主要定位 | 需要记住的概念 |
| --- | --- | --- |
| MCP | AI 应用与外部工具、数据和上下文能力的连接 | Host、Client、Server |
| A2A | 不同 Agent 之间的能力发现与任务协作 | Agent Card、消息与任务状态 |

- MCP Host：用户使用的 AI 应用，协调和管理 Client。Client：与 Server 通信的组件。Server：提供工具或上下文能力的程序。
- MCP 使用 JSON-RPC 定义交互，有助于减少逐对定制适配；标准化不等于无需实现工具、配置连接或处理权限。
- A2A 的 Agent Card 是描述身份、能力、技能、服务入口等信息的元数据；任务的动态执行状态通过任务与状态更新描述。
- 两者关注不同连接层，可以互补；接上协议并不自动具备自主闭环。

核对说明：原文将 Agent Card 简化为包含“正在做什么”的名片。这里将能力发现与动态任务状态分开表述，避免把 Agent Card 当成任务进度表。MCP 的能力范围也不只有工具。

出处：PDF 第 11 至 13 页；MCP 与 A2A 官方文档核对

## 面试易错点

| 容易说错 | 建议说法 |
| --- | --- |
| Agent 就是插件或工具调用 | 工具只是行动能力的一部分，重点是目标驱动的自主闭环。 |
| 模型自己执行 API | 模型决定调用什么，外部程序执行，结果再反馈。 |
| 模型完全不能规划或记住上下文 | 模型可以规划并利用本次上下文；系统负责持续执行和跨调用状态。 |
| 所有 Agent 必须使用向量数据库 | 记忆实现取决于任务需求，向量数据库只是一种常见选择。 |
| Agent 出错就一定能修好 | 系统能根据反馈调整，但成功与可靠性需要单独评估。 |
| MCP 与 A2A 是二选一的替代关系 | MCP 偏向外部能力接入，A2A 偏向 Agent 协作。 |

出处：PDF 第 6 至 13 页；边界澄清

## 面试回答：按这五句组织

- 追问工具：强调接口描述、调用请求、真实执行、结果回传四个环节。
- 追问记忆：先区分任务内状态与跨任务信息，再说具体实现。
- 追问协议：先说明 MCP 与 A2A 的定位，再介绍角色和能力发现。

① Agent 是围绕目标进行感知、规划、行动和反馈调整的 AI 系统，核心是自主闭环。
② LLM 负责理解、推理与生成，Agent 在系统层组织工具、状态和执行循环。
③ 模型决定用哪个工具、传什么参数，真正的调用由外部程序执行。
④ 工具结果与中间状态回到上下文，帮助它继续决策；失败时可以调整计划。
⑤ 所以不能只说“Agent 是能调工具的大模型”，还必须点出目标驱动、多步执行和结果反馈。
